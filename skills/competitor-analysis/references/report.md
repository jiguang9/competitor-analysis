# 竞品报告

竞品报告（模式④）是用户**主动运行**后生成的周期性报告，不代表后台监控或自动通知。v1.0 不提供调度和推送能力。

## 前置检查

1. 读取项目中已保存的 `config.md`（竞品清单、关注维度、市场范围、默认深度）。
2. 查找最近一份"范围兼容"的历史报告：**竞品清单、关注维度、市场范围三项必须与本次完全一致**才算范围兼容，不接受"高度重合"这类模糊判断。
3. 竞品清单、关注维度、市场范围三项中任意一项发生变化（新增/删除竞品、调整关注维度、切换市场），本次都建立**新基线**，不与旧范围的报告强行比较，并在报告中说明"配置范围已变化，本期为新基线"。

## 采集与比较流程

1. 按配置的竞品清单和维度，收集本期公开信息（默认 Quick 深度，除非用户要求 Deep）。
2. 记录每个来源的状态：成功 / 获取失败 / 需要登录或付费墙 / 未查到相关信息。这四种状态严格区分，不能互相替代（见 `data-sources.md`）。
3. 与最近一次**有效**基线比较——"有效"指该次报告的采集没有全面失败。
4. 先过滤重复信息和无实质意义的页面变动（例如网站改版导致的 HTML 结构变化、无内容差异的重新发布），再进行战略分析，避免把噪音当成信号。

## 必须标注实际日期和间隔

报告由用户手动触发，没有固定排期——两次运行间隔可能是 3 天，也可能是 2 个月，不能假设正好相隔一周。因此：

- 报告必须在开头明确标注：本期核验日期、上次有效基线的日期、两者相隔的实际天数（例如"本期：2026-08-18；上次基线：2026-08-03；相隔 15 天"）。
- 正文一律使用"本期"/"上期"，不假设两次运行之间正好相隔一周。
- 如果实际间隔明显偏离一周（例如相隔超过 30 天，或不到 2 天），在"本期监控健康状态"里提醒用户：间隔时间会影响"变化"的解读方式，间隔越长，观察到的差异越可能是长期趋势的累积而不是某一具体动作。

## 首次运行

如果没有找到范围兼容的历史报告，本次输出为"首次基线"：只呈现本期发现，不生成任何环比语言，并在报告顶部明确标注"首次基线，无环比数据"。

## 失败保护

- 全部来源采集失败时，输出"本期数据不足"，禁止输出"没有变化"这类会被误读为"已核实且没有变化"的措辞。
- 部分来源失败时，在报告的"本期监控健康状态"中列出哪些来源失败、失败类型，其余部分仍正常输出，但涉及失败来源的维度需要标注"本期未覆盖"而非直接沿用上期结论。
- 抓取失败的本期报告不能覆盖上一份有效基线——下一次运行时，比较对象仍是最近一次有效报告，而不是这次失败的报告。
- 只有本次采集**有效**（至少部分来源成功且核心维度有数据）时，才可以作为下一次报告的比较基线。

## 输出结构

- 本期核验日期、上次有效基线日期、相隔天数（首次运行则只写本期核验日期）
- 本期监控健康状态（来源成功/失败/无信号情况一览）
- TOP3 竞品动作及可能意图（每条标注 verified fact 或 inference，见 `evidence-protocol.md`）
- 与上期相比的变化（首次运行则省略此项，替换为"首次基线说明"）
- 2 条对我方的影响
- 2 条建议行动
- 跟/缓/不跟判断（见 `action-priority.md`）
- 待核实信息
- 获取失败的来源

## 阅读体验

参考课程原始经验：一份好的竞品情报报告不超过 5 分钟阅读时间。超出"3 条最重要动作 + 2 条影响分析 + 2 条应对行动"这个结构的内容容易被读者跳过，写报告时优先保证这几块的质量，而不是堆砌覆盖面。

## 监控频率建议（供用户参考，非强制）

不同类型的信息不需要同频关注：

| 信息类型 | 建议频率 |
|---|---|
| 舆情 / 爆款内容 | 每周一次，纳入报告 |
| 价格 / 促销变化 | 每周一次；大促期间可提高到每日（需用户手动运行） |
| SEO / 官网页面结构 | 每月一次，重点看新增落地页和关键词布局 |
| 品牌定位 / 产品线 | 每季度一次，综合评估战略方向变化 |

这些建议用于帮助用户决定何时手动重新运行报告，v1.0 不会自动按此频率触发。
